# ADR 0001 — Notificações assíncronas com fila de mensagens (RabbitMQ)

**Status:** Aprovado

**Data:** 10/11/2026

**Autor:** Fernando Damasceno

## Contexto

No fluxo de reserva do FabLab Manager, o sistema precisa avisar as pessoas em vários momentos (RF25):

- o administrador/técnico, quando chega uma nova solicitação;
- o solicitante, quando a reserva é aprovada ou negada (com a justificativa do RF08).

Esses avisos são enviados pelo **Serviço de Notificação**, que é um sistema externo. Se a API do FabLab chamar esse serviço de forma síncrona, ou seja, esperando a resposta, aparecem alguns problemas:

- se o Serviço de Notificação estiver lento, a aprovação da reserva também fica lenta para o técnico;
- se o Serviço de Notificação estiver fora do ar, a aprovação pode dar erro mesmo estando tudo certo com a reserva;
- se o aviso falhar, ele se perde e o solicitante não fica sabendo da decisão.

A notificação é importante, mas não deveria travar a regra principal, que é registrar a reserva e a decisão.

## Decisão

Usar uma **fila de mensagens com RabbitMQ** entre a API FabLab e o Serviço de Notificação.

Funcionamento:

1. A API (FastAPI) salva a mudança da reserva no PostgreSQL.
2. Depois, a API publica um evento na fila (por exemplo, `reserva_aprovada`) usando o protocolo AMQP e responde ao usuário na hora, sem esperar o envio do e-mail.
3. O Serviço de Notificação consome os eventos da fila e envia os avisos.
4. Se o Serviço de Notificação estiver fora do ar, as mensagens ficam guardadas na fila (fila durável) e são entregues quando ele voltar.

No Diagrama de Sequência isso aparece nas mensagens assíncronas `notificar(...)` (seta `-)`), e no C4 aparece no contêiner **Fila de Notificações (RabbitMQ)**.

### Alternativas consideradas

| Alternativa | Por que não foi escolhida |
|---|---|
| Chamar o Serviço de Notificação direto por HTTP (síncrono) | A aprovação fica dependente de um serviço externo; se ele cair, a reserva dá erro. |
| `BackgroundTasks` do FastAPI | Mais simples, mas a tarefa roda na memória do servidor: se a API reiniciar, a notificação se perde. |
| Kafka | Resolve, mas é bem mais complexo de configurar e manter do que o FabLab precisa. |

## Consequências

**Vantagens**

- A API responde mais rápido, porque não espera o e-mail ser enviado.
- Uma falha no Serviço de Notificação não impede aprovar ou negar reservas.
- As mensagens não se perdem quando o Serviço de Notificação está fora do ar.
- Fica fácil adicionar outros consumidores no futuro (por exemplo, um painel em tempo real).

**Desvantagens e riscos aceitos**

- Mais um serviço para rodar e manter (RabbitMQ no `docker-compose`).
- A notificação pode chegar com alguns segundos de atraso.
- Se a API salvar a reserva no banco e cair antes de publicar o evento, o aviso pode não ser enviado. Por enquanto aceitamos esse risco; uma melhoria futura seria guardar o evento no próprio banco e publicar depois (padrão *Outbox*).
- A mesma mensagem pode ser entregue mais de uma vez, então o Serviço de Notificação precisa ignorar avisos repetidos.
